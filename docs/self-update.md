# 版本自更新

设置页提供版本检查、下载校验、手动安装及定时策略。默认关闭定时任务，可选择仅检查提示，或在维护窗口自动安装；窗口使用页面显示的服务时区，支持跨午夜。

## 构建与部署识别

| 类型 | 行为 |
|---|---|
| 源码自行编译 | 检查稳定版，继续用原构建/启动脚本更新，禁止Release覆盖安装 |
| Release二进制 | 程序目录可写时支持手动或定时安装 |
| systemd | root运行、当前服务单元归属可验证、systemd-run可用时通过独立瞬态助手安装；非root或权限不足时只检查，由部署管理员在外部更新 |
| Docker | 只检查，使用镜像更新并重建容器，保留数据卷；不覆盖容器程序，不要求Docker socket |

源码构建默认没有Release标记，手动设置类似v0.4.0的版本号不会改变这一点。正式发布工作流写入发布来源、提交及平台信息；工作区内的程序仍受源码保护。早期Release未包含这些标识，需要先用现有部署方式升级到支持自更新的正式版本。

## 更新流程

1. 从构建标识对应的GitHub仓库读取最新稳定版，不接受任意下载地址，不自动降级或安装预发布版。
2. 匹配系统/架构，下载程序包与SHA-256文件；GitHub提供摘要时额外核对。包和程序最多128MiB，拒绝危险路径、特殊文件及多个程序。
3. 验证候选程序的来源、版本、提交、平台及数据库版本。源码和容器不能通过管理台安装。
4. 安装时先停止接收新请求，最多等待已有调用60秒；超时取消更新，旧服务恢复接单。随后停止后台维护，生成数据库、主密钥、渠道状态及配置的完整备份，保留旧程序。
5. 独立助手在确认数据锁释放后替换程序。新版在维护状态下启动，核对版本/提交/schema、数据库quick_check和已保存Key的解密验证，完成后开放请求。
6. 新版启动失败时，确认实例停止后恢复更新前程序及数据。若无法确认停机或开放结果，停止自动恢复并保留副本，请部署管理员核实；不冒险覆盖新的用户写入。

切换存在短暂维护窗口，期间新请求收到503及Retry-After；不是零停机。管理登录可能在重启后失效，需要重新登录。

## 自动策略与恢复材料

自动安装只接受数据库版本不变的稳定版；数据库迁移必须手动勾选确认。同版本重发通过产物指纹识别，自动安装重发产物默认关闭。下载或安装失败后至少等待一小时，同一产物每天最多自动尝试一次；手动操作不受这个重试间隔约束。

更新事务、日志和恢复副本位于数据目录的`.updates/`，包含敏感配置和凭据，不能作为静态目录公开。成功后仅清理此前已完成的更新事务及本次候选，保留当前更新前程序与完整备份；失败及需要人工恢复的材料保留。它们不纳入自动日备份归档，不会导致递归备份。

SSH、容器或人工恢复前，应先核实事务的`phase`，停止相关实例并确认数据锁释放。涉及迁移的回退必须同时恢复匹配的程序和完整数据，不能只替换旧二进制。`acceptance_unknown`表示新版可能已经开放，不应直接回滚覆盖数据。
